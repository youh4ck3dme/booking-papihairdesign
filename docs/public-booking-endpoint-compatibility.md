# Public booking endpoint compatibility

Read-only inspection of the existing production JavaScript asset `BookingPage-BePC1N1-.js` on `https://nimble-agenda-swart.vercel.app` showed a client behavior absent from the repository baseline: the deployed page first calls `supabase.rpc('create_public_booking', payload)` and falls back to `functions.invoke('create-public-booking', { body: payload })` only for PostgREST error code `PGRST202` (missing function/signature). No production reservation request was made to obtain this evidence. The observed production source metadata was `3e9a5887a4becb17cf298a65b2c93a1039dbd9f3`; that commit was not available through the configured repository's refs, so this compatibility behavior is preserved explicitly rather than claiming a cherry-pick or equivalent production tree.

`src/lib/create-public-booking.ts` preserves that RPC-first behavior using the same unprefixed payload keys: `business_id`, `service_id`, `employee_id`, `start_at`, `customer_name`, `customer_email`, and optional `customer_phone`. Both paths retain the existing response shape and BookingPage success/error handling. A conflict, authorization failure, network failure, or application-level error never triggers a second mutation. The fallback is only permitted when the primary RPC is explicitly absent; no function implementation or new reservation backend is added by this change.

Unit tests invoke this actual helper with a mock client to prove single primary success, one missing-RPC fallback and absence of duplicate attempts for all other failures. Browser confirmation uses an explicitly enabled, fully local reservation fixture; it is not a real reservation or proof of live endpoint availability. Before a production release, verify the actual configured backend project's schema and endpoint compatibility; do not infer that the repository's fallback project is the live backend or change production credentials.

## Preserved public catalogue boundaries

The same read-only production source map showed two additional catalogue contracts that must remain intact: `businesses` is projected to `opening_hours, lead_time_minutes, max_days_ahead`, and provider eligibility comes from the existing `get_public_bookable_employees({_business_id, _service_id})` RPC. The frontend now preserves that exact business projection; it attaches the already-known query business ID locally for the bounded busy-interval request. Employee rows contain only `id`, `display_name`, and `photo_url`. It no longer loads public-page memberships, private employee fields, or employee-service mappings to reproduce authorization rules in the client.

The existing provider RPC is called initially with a null service and again for the selected service. Service changes abort old requests and clear worker/date/time choices. Its backend eligibility rules are authoritative. The existing schedule read remains scoped to returned employee IDs. This release does not invent or redefine that deployed RPC's SQL; its actual schema/permissions remain an explicit live-project verification prerequisite.
